## Purpose

This document defines what belongs on the site, where it belongs and how much detail it should contain.

## Content types

### Experiments

Substantial, evolving project stories organised around a question.

Use when the work contains:

- a worthwhile problem or hypothesis;
- meaningful engineering decisions;
- evidence or artefacts;
- learning that can be explained;
- enough depth to justify a durable page.

### Research notes

Focused observations, technical investigations or explanations connected to one or more experiments.

A note may cover:

- a design decision;
- an architecture pattern;
- a failed approach;
- a benchmark;
- a physics or AI concept;
- a short implementation discovery.

Notes do not need to become polished long-form articles.

### Observations

Shorter records of something surprising, useful or unresolved. This is a future content type and is not required for MVP.

### Career context

A concise narrative explaining how I moved through support, systems, development, leadership, cloud and AI. It complements the CV without reproducing every role.

### Current obsessions

A small, maintained list of questions and topics I am actively thinking about. It should change over time and should not become a skills list.

## What stays in GitHub

GitHub is the home for:

- complete public source;
- issue history;
- implementation-level documentation;
- releases;
- setup instructions;
- detailed contribution material.

The portfolio links to this evidence but does not duplicate it.

## What stays private

Keep private:

- employer or customer intellectual property;
- confidential data;
- security-sensitive implementation detail;
- credentials, tokens and infrastructure secrets;
- source code that is not mine to publish;
- repositories that require review before external access.

Private repository availability may be stated, but access is never promised automatically.

## Content selection test

Before publishing, ask:

1. Does this help explain how I think?
2. Is there a real story or lesson?
3. Is the evidence mine to share?
4. Is the maturity represented honestly?
5. Does the content duplicate the CV or GitHub unnecessarily?
6. Would a relevant reader learn something useful?

## Depth model

Every experiment should support three reading levels:

### Thirty-second skim

- question;
- summary;
- current state;
- main outcome or learning.

### Five-minute read

- problem;
- approach;
- key decisions;
- evidence;
- lessons.

### Technical deep dive

- architecture;
- alternatives;
- implementation detail;
- failures;
- linked notes and source.

## Editorial maintenance

Content should be reviewed when:

- the project state changes;
- a major technical direction changes;
- an experiment becomes public or production-ready;
- a claim becomes outdated;
- a new lesson materially changes the story.

Use `last investigated` rather than implying every edit is a product release.

## Acceptance criteria

- [ ] Experiments, notes and career context have distinct purposes.
- [ ] Private source is supplementary rather than required.
- [ ] Every experiment supports skim and deep-read paths.
- [ ] Content selection prioritises learning and evidence.
- [ ] The site does not become a copy of the CV or GitHub profile.

# Clarity Before Cleverness

| Field | Value |
|---|---|

| **Status** | Accepted |

| **Owner** | I / repository maintainer |

> If a simpler explanation or implementation achieves the same outcome, prefer it.

Cleverness is not automatically bad. Some projects genuinely require unusual abstractions or experimental interfaces.

The problem begins when the clever part becomes the point.

The public experience should make the difficult ideas easier to understand. It should not require the reader to decode the site before they can decode the work.

This principle applies to:

- navigation;
- writing;
- diagrams;
- component APIs;
- data models;
- dependencies;
- animation;
- deployment architecture.

Complexity must have a job.

## Test

Before accepting a clever solution, ask:

- What reader or engineering problem does it solve?
- Is the simpler version genuinely insufficient?
- Does it create maintenance or accessibility cost?
- Will the value survive after the novelty fades?

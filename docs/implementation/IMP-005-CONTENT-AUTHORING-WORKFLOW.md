## Purpose

This document defines how experiment and research-note content moves from an idea to public publication.

## Workflow

### 1. Capture the trigger

Record the original observation, request, frustration or question before polishing it into a narrative. Preserve the reason the work began.

### 2. Create a draft record

Create the content file with:

- stable identifier;
- provisional slug;
- draft visibility;
- working title;
- central question;
- current state;
- known evidence sources;
- confidentiality notes.

### 3. Build the evidence inventory

Collect only evidence that can be published or safely transformed:

- screenshots;
- diagrams;
- public code;
- sanitised code excerpts;
- metrics that can be substantiated;
- design notes;
- decisions and trade-offs;
- failed approaches;
- lessons.

Mark every item as public, sanitised, private, request-only or unavailable.

### 4. Write the concise layer

Before writing the full story, produce:

- one-sentence question;
- short summary;
- why it mattered;
- what was built;
- current state;
- strongest piece of evidence.

This layer supports cards, introductions, metadata and fast-reading visitors.

### 5. Write the deep layer

Develop the narrative using the engineering-notebook sequence where it fits:

1. observation;
2. question;
3. context;
4. initial hypothesis;
5. experiment or prototype;
6. architecture and important decisions;
7. failures or surprises;
8. result;
9. lessons;
10. next steps.

Do not force every story into identical headings. The schema provides consistency; the writing should still feel human.

### 6. Validate claims

For every important claim, ask:

- Can I show evidence?
- Could I explain this honestly in an interview?
- Am I implying production maturity that did not exist?
- Does this reveal information that is not mine to publish?
- Is this my direct knowledge, or an inference?

Unsupported claims must be removed, qualified or marked as hypotheses.

### 7. Technical and editorial review

Review in two passes:

- technical accuracy, architecture and evidence;
- clarity, voice, pacing and first-person authenticity.

Rendered review is mandatory because headings, diagrams and code blocks can read differently on the page than in source.

### 8. Publication review

Before changing visibility to public:

- run schema validation;
- run broken-link checks;
- inspect metadata and social preview;
- verify image alternatives;
- check related-content links;
- confirm no draft markers or confidential notes render;
- complete the content-entry definition of done.

### 9. Maintain the record

Use `lastInvestigated` or equivalent metadata for meaningful updates, not trivial typo fixes. Preserve important changes to assumptions or direction in the narrative rather than silently rewriting history.

## AI-assisted writing rules

AI may help organise notes, identify gaps, tighten prose and propose headings. It must not invent:

- motivations;
- outcomes;
- metrics;
- customer reactions;
- technical decisions;
- failure stories;
- repository contents.

Anything generated by AI remains a draft until I have verified that it is true and sounds like me.

## Acceptance criteria

- [ ] every public content item has a traceable evidence inventory;
- [ ] publication requires both technical and editorial review;
- [ ] confidentiality is considered before drafting, not after publication;
- [ ] AI-generated prose cannot become evidence;
- [ ] concise and deep reading layers remain aligned.

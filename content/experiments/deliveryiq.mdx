## The Question

Every delivery tool I have used is very good at recording work and much less good at
improving it. A sprint board can tell you a story is In Progress; it cannot tell you the
story was never ready to be started. Missing acceptance criteria, hidden dependencies
and architectural questions usually surface after implementation has begun, which is the
most expensive possible time to discover them.

I wanted to explore whether AI could be used earlier in the delivery lifecycle — not to
generate code, but to improve the quality of work before it reaches developers.

## The Problem

Judging whether work is genuinely ready requires context that rarely lives in one place.
Part of the picture is in Azure DevOps. The original business intent might be in
Confluence. Architectural knowledge lives in the codebase, and operational constraints
often exist only in the heads of whoever has been on the team longest.

Most delivery tooling treats those sources independently. As a result, readiness becomes
a judgement call made manually during refinement — or discovered after development has
already started.

The obvious fix — bolting a chat window onto an existing tracker — did not convince me.
A chatbot can answer questions about work items, but it does not change the quality of
the work entering a sprint. Asking better questions of unready work felt like polishing
the problem.

## The Hypothesis

My hypothesis was that if work items were evaluated against an explicit readiness rubric
before development began, many of the questions normally discovered during
implementation could be resolved during planning instead, where they are cheap.

The second half of the hypothesis took me three rebuilds to accept: the delivery tracker
should not be replaced. DeliveryIQ sits alongside it — Azure DevOps stays as the system
of record, and AI provides analysis, review and recommendations over synchronised
delivery data.

I want to be clear about the framing: this is still a hypothesis. The platform
demonstrates the workflow; I have not yet measured whether it improves delivery
outcomes.

<Callout variant="note" title="Current implementation">
  **Core capabilities:** Azure DevOps and Confluence synchronisation; readiness scoring
  against a four-category rubric; deterministic quality gates; development and test
  prompt generation; five role-based review agents; documentation and code retrieval
  using pgvector; human-controlled write-back to Azure DevOps; a Model Context Protocol
  (MCP) server exposing platform tools to external agents; and delivery-stage specific
  views.

**Experimental capabilities:** an orchestration kernel with adaptive model routing,

## The Approach

The system centres on a single workflow. A work item syncs in from Azure DevOps together
with its supporting Confluence documentation, and a model scores the combined context
against a rubric with four categories:

- intent and clarity
- acceptance criteria and testability
- dependencies and integration impact
- technical and non-functional requirements

Each category contributes to an overall readiness score. Rather than letting the model
decide what happens next, DeliveryIQ separates judgement from policy: the model performs
the assessment, and deterministic thresholds — seventy overall, with minimum scores on
acceptance criteria and one of the technical categories — decide what the resulting
score is allowed to unlock.

Work below the gate generates questions and recommendations, aimed at whoever can answer
them. Work that passes can have implementation and test prompts generated, which a human
then decides whether to apply back to Azure DevOps. The write-back is a button, not a
background job, and it leaves an audit event behind.

Around that loop sit five review agents with single, narrow responsibilities — a tech
lead, a non-functional-requirements specialist, a UX and product voice, a delivery
manager and a designated sceptic — each reading the same work item from its own angle.
Their purpose is not to rewrite requirements but to expose risks and missing information
before implementation begins. The AI questions more than it writes, and the analyst
keeps ownership of the words.

## Architecture

A Next.js front end provides a view per delivery stage. A .NET 8 core API owns identity,
persistence and the Azure DevOps and Confluence integrations. A Python FastAPI service
does the AI work — analysis, retrieval and prompt generation — using Azure AI Foundry
models. Supporting services include PostgreSQL with pgvector for operational and vector
data, Redis for caching and RabbitMQ for messaging between the services. The AI service
also exposes the platform's tools over the Model Context Protocol, so an external agent
can work with the same delivery data the UI shows.

Model routing is not a fixed map of cheap-model-for-this, strong-model-for-that. It is a
cost-weighted bandit: each model carries hand-written priors per task type, Thompson
sampling picks a route, and feedback from completed tasks updates the posterior. Task
classification deliberately never touches a model — it is cheap heuristics, on the
grounds that spending inference to decide how to spend inference is the wrong shape.

Every scoring run is recorded with the model and provider that served it, a snapshot of
the work item exactly as it was scored, and an audit event for anything applied back to
Azure DevOps. When a score looks wrong, I can answer "what did it actually see?" — which
is a different and better question than "why did it say that?"

Alongside the core runtime sits the experimental orchestration kernel, responsible for
adaptive routing, planning and verification. It runs, but it currently exists as an
optional execution path while the simpler direct workflow remains the primary
implementation. That separation is deliberate: experimentation should not complicate the
product's main workflow until it demonstrates clear value.

## Trade-offs

- **Integrate rather than replace.** Keeping Azure DevOps as the system of record costs
  real synchronisation code — snapshots, pending-push states, and a careful line between
  local edits and remote truth. What it buys is a tool a real team could adopt without
  migrating anything.
- **AI judgement, deterministic policy.** Models are good at interpreting ambiguous
  information and less suited to making operational decisions. DeliveryIQ uses AI for
  assessment and conventional software for enforcement.
- **Questions over automation.** Automatically rewriting requirements risks replacing
  missing information with plausible-looking text. Returning targeted questions keeps
  ownership with the analyst while still accelerating refinement.
- **Research versus product.** The orchestration kernel and coding agent explore more
  autonomous workflows, but the central hypothesis is about delivery readiness. Those
  components stay isolated until they justify their complexity — which means every flow
  has two code paths, one direct and one orchestrated, and I maintain both.

## What Went Wrong

The biggest lesson was one of focus. What began as a readiness gate for one role
accumulated review agents, retrieval, orchestration, a coding agent, an MCP server and a
view for every stage of delivery. Each addition was individually interesting; together
they risked distracting from the original question. The codebase is platform-sized. The
evidence is still prototype-sized.

The kernel is the clearest example. I built the most architecturally interesting
component in the system — learned routing, verification passes, repair and escalation —
and then shipped it turned off, because the direct path was already working and
switching the product's spine onto it never became urgent. Building sophisticated
infrastructure before validating the underlying hypothesis was probably the wrong order.
A flag that ships disabled is a verdict, even when nobody says it out loud.

There is also a smaller defect I want on record: on the kernel path, a readiness run
that comes back without a valid payload can still be marked succeeded, with the model
name recorded as "stub". It is logged honestly, but a run that succeeds without a model
is a silent fallback in a system whose entire pitch is that every output is accountable.

The broader lesson: generating AI outputs is relatively easy. Building trustworthy
workflows around those outputs is where most of the engineering effort lies.

## Lessons

- AI should assist delivery decisions rather than own them.
- Deterministic policy belongs after probabilistic judgement, not before it. Scores are
  cheap; what they unlock is where the discipline goes.
- Existing delivery tooling is better extended than replaced. The versions of this idea
  that tried to own the data model produced better demos and less adoptable tools.
- Agents earn trust by asking questions, not by writing prose. The five reviewers are
  useful precisely because none of them is allowed to be the author.
- Auditability is cheapest as a snapshot. Recording exactly what the model saw answers
  most disputes before they become philosophical.
- An optional component is a component on trial, and the default value of its feature
  flag is the interim verdict.

## Current State

DeliveryIQ is a working prototype, not a product. The current repository is the third
rebuild of the idea. It runs locally end to end: synchronisation, readiness scoring, the
quality gate, prompt generation, the review agents and the write-back flows all work.
The kernel and the coding agent run but are not yet trusted with the product's spine.

What does not exist is the measurement. The platform demonstrates that AI-assisted
delivery workflows can be built; whether teams using readiness gates see fewer
interruptions, less rework and more predictable delivery than conventional refinement is
the claim the whole system is built on, and it is still untested. The repository is
private because it is shaped around a real team's workflow, but I am happy to walk
through the architecture and the code.

- What evidence best predicts whether work is genuinely ready?
- Where should the boundary sit between AI assistance and delivery automation?

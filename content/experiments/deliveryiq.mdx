## The Question

Every delivery tool I have used is very good at recording work and much less good at
improving it. The board can tell you a ticket is In Progress; it cannot tell you the
ticket was never ready to be started. The expensive failures — the missing acceptance
criteria, the dependency nobody owned, the feasibility problem — surface mid-sprint,
which is the most expensive possible time to learn about them.

So I wondered: what if the tool did the admin, and the humans did the thinking? Not a
chatbot bolted onto a tracker, but a workflow with AI designed into it from the start.

## The Problem

Work items vary wildly in quality, and the knowledge needed to judge them does not live
in the tracker. It lives in a wiki brief, in the codebase, and in the heads of whoever
has been on the team longest. A board full of green columns can still be full of work
that is not ready to build, and nothing in the tool will say so until a developer picks
the ticket up and starts asking questions.

The obvious fix — bolting a chat window onto an existing tracker — did not convince me.
A chatbot can answer questions about the data, but it does not change what is allowed
into a sprint. Asking better questions of unready work felt like polishing the problem.

## The Hypothesis

My hypothesis was that if readiness were scored before work started — against an
explicit rubric, with a hard gate on what the scores unlock — the expensive mid-sprint
discoveries would move to before the sprint, where they are cheap. The system should ask
its clarifying questions while the work is still a conversation, not an obligation.

The second half of the hypothesis took me three rebuilds to accept: the delivery tracker
should not be replaced. The current version keeps Azure DevOps as the system of record
and treats AI strictly as leverage over it.

I want to be clear about the framing: this is still a hypothesis. I have not measured
whether gated work gets interrupted less, and I am deliberately not claiming it until I
can support it with evidence.

## The Approach

I started with the narrowest loop I could defend. Work items sync in from Azure DevOps;
the Confluence brief they came from is linked alongside them; a model scores each item
against a rubric with four categories — intent and clarity, acceptance criteria and
testability, dependencies and integration impact, technical notes and non-functional
requirements — each worth twenty-five points. A deterministic gate sits after the model:
seventy overall, at least fifteen on acceptance criteria, at least twelve on one of the
technical categories. Nothing below the gate can have implementation prompts generated
for it. Instead it gets questions, aimed at whoever can answer them.

When an item passes, the system drafts a development prompt and a test prompt, and a
human decides whether either is written back to the work item. The write-back is a
button, not a background job, and it leaves an audit event behind.

Around that loop I added reviewers: five agents with single, narrow responsibilities — a
tech lead, a non-functional-requirements specialist, a UX and product voice, a delivery
manager and a designated sceptic — each reading the same work item from its own angle.
The design philosophy written at the top of that module is the one I hold to: the AI
questions more than it writes, and the analyst keeps ownership of the words.

## Architecture

The current system is eight containers: a Next.js front end with a view per delivery
stage, a .NET 8 core API that owns identity, the Azure DevOps and Confluence
integrations and persistence, a Python FastAPI service that does the AI work, the
orchestration kernel, the coding agent, PostgreSQL with pgvector, Redis for caching, and
RabbitMQ for messaging between the services. The AI service also exposes the platform's
tools over the Model Context Protocol, so an external agent can work with the same
delivery data the UI shows.

Model access goes through Azure AI Foundry to both Anthropic and OpenAI models, with an
optional path to a locally hosted model for development. Routing between them is not a
fixed map of cheap-model-for-this, strong-model-for-that. It is a cost-weighted bandit:
each model carries a card of hand-written priors per task type, Thompson sampling picks
a route, and feedback from completed tasks updates the posterior. Task classification —
deciding what kind of work a request is — deliberately never touches a model at all; it
is cheap heuristics, on the grounds that spending inference to decide how to spend
inference is the wrong shape.

Two decisions shaped everything else:

1. **The model proposes, the gate disposes.** An earlier version of this page said
   deterministic rules run first and the model handles what is left. The code is the
   other way round, and the code is right: the model does the reading and produces the
   scores, and deterministic thresholds decide what those scores are allowed to unlock.
   Judgement is cheap to generate; consequences are gated.
2. **Every run leaves a trail.** Each scoring run is recorded with the model and
   provider that served it, a snapshot of the work item exactly as it was scored, and an
   audit event for anything applied back to Azure DevOps. When a score looks wrong, I
   can answer "what did it actually see?" — which is a different and better question
   than "why did it say that?"

## Trade-offs

- **Integrating versus rebuilding.** Earlier versions of this experiment wanted to own
  the delivery model. The current one concedes that the tracker your team already uses
  is the system of record, and pays for that concession in synchronisation code:
  snapshots, pending-push states, and a careful line between local edits and remote
  truth. What it buys is a tool a real team could adopt without migrating anything.
- **Autonomy versus trust.** Everything that writes to the tracker is a human-triggered
  apply step. Except the coding agent, which can commit and raise pull requests, and
  which I keep at the far end of the leash behind its own review gates. Holding both of
  those positions at once is uncomfortable, and I notice that the part of the system I
  trust least is the part with the most autonomy.
- **Learned routing versus a fixed map.** The bandit is more honest than a hand-written
  routing table — it admits routing is an empirical question. But its cold-start priors
  are numbers I wrote myself, which means today it is mostly my judgement wearing a
  Bayesian costume. It only becomes better than a fixed map once there is enough
  feedback, and a single-team prototype generates feedback slowly.
- **A kernel versus a function call.** The orchestration kernel — classify, plan,
  execute, verify, repair — is the most architecturally interesting thing in the
  repository, and the flag that enables it ships set to false. Every flow therefore has
  two code paths, one direct and one orchestrated, and I maintain both. That is a real
  cost I am paying for an option I have not yet exercised.

## What Went Wrong

The most instructive failure was not in the code. It was on this page. The previous
version of this write-up said the system ingested standup transcripts and produced a
morning digest of blocked work, that Semantic Kernel orchestrated the agents, and that
nothing had write access to anything. The repository contains none of those things.
They were plans from an earlier phase that had quietly turned into memories — the same
failure I caught on Morris, which apparently I need to keep re-learning: writing a page
against the repository is a stronger audit than any recollection.

The kernel is the second failure, and it is the over-engineering kind. I built the
cleverest component in the system — learned routing, verification passes, repair and
escalation — and then shipped it turned off, because the direct path was already working
and switching the product's spine onto the new one never became urgent. A flag that
ships disabled is a verdict, even when nobody has said it out loud.

The third one is small and I flagged it deliberately: on the kernel path, a readiness
run that comes back without a valid payload can still be marked succeeded, with the
model name recorded as "stub". It is logged honestly — the word stub is right there in
the run record — but a run that succeeds without a model is the Morris silent-fallback
lesson wearing a new coat, in a system whose entire pitch is that every output is
accountable.

And underneath all three: sprawl. What began as a readiness gate for one role now has a
view for every stage of delivery, an assurance and test-planning surface, a coding
agent, a Model Context Protocol server and a demo mode. The codebase is platform-sized.
The evidence is still prototype-sized. My own writing rules say never to call a
prototype a platform merely because the codebase is large, and this project is exactly
why that rule exists.

## Lessons

- Put the deterministic part after the model, not before it. Scores are cheap;
  what they unlock is where the discipline belongs.
- Agents earn trust by asking questions, not by writing prose. The five reviewers are
  useful precisely because none of them is allowed to be the author.
- The system of record should stay where it is. The versions of this idea that tried to
  own the data model produced better demos and less adoptable tools.
- An optional component is a component on trial, and the default value of its feature
  flag is the interim verdict.
- Auditability is cheapest as a snapshot. Recording exactly what the model saw answers
  most disputes before they become philosophical.
- I cannot be trusted to describe my own projects from memory. This is the second page
  on this site that had to be corrected against its repository, and I assume it will
  not be the last.

## Current State

DeliveryIQ is a working prototype, not a product. The current repository is the third
rebuild of the idea and holds 116 commits between January and March 2026. It runs
locally as an eight-container composition: synchronisation, readiness scoring, the
quality gate, prompt generation, the review agents and the write-back flows all work
end to end. The kernel and the coding agent run but are not yet trusted with the
product's spine.

What does not exist is the measurement. I have no evidence yet that gated work gets
interrupted less, which is the claim the whole system is built on. The repository is
private because it is shaped around a real team's workflow, but I am happy to walk
through the architecture and the code.

## Next Questions

- What is the smallest honest evaluation of the core claim — do items that pass the gate
  get interrupted mid-sprint less than items that were started anyway?
- The kernel needs a decision: switch the spine onto it or delete it. Which?
- What feedback signal should count as success for a routing decision, when "the model
  answered" and "the answer helped" are very different events?
- How much of the synchronisation layer is essential, and how much is the cost of one
  team's particular Azure DevOps configuration?
- The run record keeps scores, snapshots and audit events but not the full prompt
  transcript. Is that a pragmatic trade or a hole in the accountability story?
